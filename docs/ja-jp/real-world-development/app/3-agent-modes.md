最初にプロジェクトへ小さな機能を追加しました。より大きな変更には、さらに堅牢なプロセスが必要です。GitHub Copilot app は組織の既存のフローに沿って作業できるため、適切なものを適切な方法で構築できます。このレッスンから数回にわたり、一般的なエージェント主導の開発プロセスを実践します。Issue から新機能を開始し、コードが有効で機能が期待どおりに動作することを確認して、最終的にプロジェクトへマージします。

> [!NOTE]
> 機能のワークフローを進める間は、同じセッションを使用します。通常はファイルの種類ごとに異なるセッションやプルリクエスト (PR) を使いますが、ここでは中心となる概念に集中できるよう手順を簡略化します。

このレッスンでは、次の内容を学習します。

- GitHub Issue から新しいエージェントセッションを開始する。
- **Plan** モードで要件を定義する。
- **Autopilot** モードを使用して新機能を実装する。
- コードをレビューする。
- ブラウザーキャンバスで機能を手動で検証する。

この機能の作業を続けながら、リポジトリの指示を更新し、既存の quality-checks スキルをカスタマイズして、Model Context Protocol (MCP) による検証を追加し、品質保証 (QA) エージェントを作成して、機能の PR を開きます。

## シナリオ

Tailspin Toys のカタログが増え、訪問者がゲームをカテゴリーとパブリッシャーで絞り込む機能が必要になりました。バックログの Issue に機能は記載されていますが、カテゴリーの組み合わせ方など、コーディング前に合意が必要な詳細があります。Plan モードで決定事項を整理してから、Autopilot による範囲を限定した実装を承認します。

## 背景

AI コーディングエージェントを開発フローに導入しても、基本は変わりません。むしろ、基本はさらに重要になります。多くの開発者は、次のようなフローに従います。

1. 必要な作業の詳細が記載された Issue を開く。
2. 構築する内容の計画を作成する。
3. コードを構築してレビューする。
4. テストを実行してコードを検証する。
5. 新機能を手動で検証する。
6. PR を作成する。
7. コードのレビューと継続的インテグレーション (CI) プロセスが成功したら、コードをマージする。

> [!NOTE]
> 正確な手順はチームや組織によって異なりますが、多くの場合は上記の流れを調整したものです。

この標準的なアプローチを守ることで、AI が生成したコードが要件を満たし、人間が作成したコードと同じ審査プロセスを通るようにできます。

## セッションモード

**セッションモード**は、エージェントの自律性を制御します。プロンプトフィールドの下にあるドロップダウンから設定し、いつでも変更できます。

- **Interactive**: 開発者とエージェントが共同で作業します。エージェントは変更を提案し、続行前に入力を待ちます。
- **Plan**: エージェントが最初に計画を作成します。実行前に計画をレビューして承認します。
- **Autopilot**: エージェントが自律して作業し、入力を待たずにコードを作成し、テストを実行して反復します。

Plan モードで開始し、計画をレビューしてから、Autopilot で実装します。

## Issue からセッションを開始する

星評価の PR がマージされ、ローカルの `main` が最新であることを確認してから、新しい作業を始めます。

1. サイドバーの **Sessions** で Tailspin Toys リポジトリのフォルダーを選択し、リポジトリ上部のナビゲーションで **Issues** を選択します。**Allow users to filter games by category and publisher** を開きます。これは用意された既存の Issue なので、新たに作成する必要はありません。
2. **New session** を選択し、更新済みの `main` に基づく **new working tree** を選びます。

    ![GitHub Copilot app の Issue ビューで、New session ボタンを矢印で示した画面](../../../_images/app-new-session-from-issue.png)

3. Issue がセッションに添付されていることを確認し、モードセレクターで **Plan** を選択します。

> [!NOTE]
> Node.js または npm が見つからない場合は、エージェントに `node --version` と `npm --version` を実行するよう依頼します。ターミナルでは動作するのにセッションでは見つからない場合、アプリの PATH またはバージョンマネージャーの設定を確認し、アプリを完全に終了して再起動します。失敗した操作とチェックを再試行してください。エージェントが npm を見つけられないという理由だけで、npm を再インストールしないでください。

## フィルター機能を計画する

計画を立てることで、Copilot がコードを書く前にアプローチをレビューできます。Issue から開始したため、Copilot は機能のリクエストをすでにコンテキストとして持っています。以下のプロンプトを送信し、計画を確認します。

1. 次のプロンプトを送信します。

    ```plaintext
    Build this feature.
    ```

2. Copilot の質問に回答し、Issue の受け入れ条件と計画を照らし合わせます。カテゴリーとパブリッシャーによる絞り込み、アクセシブルなコントロール、データアクセスの変更、テストが含まれていることを確認します。複数カテゴリーをどう組み合わせるか、一致するゲームがない場合にどうなるかなど、不明確な動作について話し合います。
3. プロジェクトの既存ツールを使った lint、単体テスト、エンドツーエンド (E2E) テスト、型チェックが計画に含まれていることを確認します。計画はフィルター機能の実装とテストに絞り、PR は品質ワークフローの完了後に作成します。
4. 計画に修正が必要な場合は承認前に変更を依頼します。後で検証できるよう、Issue の URL と合意した追加の取り決めを控えておきます。

## Autopilot を明示的に承認する

計画に納得したら、実装を開始する前に内容と選択中のモードを確認します。

1. **Approve and implement this plan**、または使用中のバージョンで表示される同等のオプションを選択します。
2. 選択中のモード表示が **Autopilot** になっていることを確認します。計画の承認によってモードが自動的に切り替わるとは限りません。
3. Copilot が実装を進める間、計画に沿ってコードを生成し、テストを実行していることを確認します。

> [!NOTE]
> 承認するとすぐに実装が始まる場合があるため、先に計画をレビューしてください。依存関係の不足やポート競合が報告された場合は、チェックを完了と判断する前にセットアップの問題を解決します。停止してよいのは、自分で起動したサーバーだけです。

## 実装をレビューして検証する

生成されたコードも、他のコードと同じようにマージ前にレビューします。実装とチェックの結果を確認してから、サイトをブラウザーで開きます。

1. **Changes** を開き、フィルター機能の実装とテストを確認します。
2. 複数カテゴリーとパブリッシャーの組み合わせも含め、変更を Issue と承認した追加の取り決めに照らし合わせます。既存のリポジトリの指示に従っていることも確認します。
3. lint、単体テスト、E2E テスト、型チェックの出力を確認します。スキップされたチェックは成功ではありません。
4. 実装を受け入れる前に失敗を解消し、該当するチェックを再実行します。Playwright の E2E 設定はビルドしてプレビューを配信し、ローカルサーバーを再利用できます。テスト対象が以前のレッスンではなく、この worktree のサーバーであることを確認します。

## 新機能を確認する

ブラウザーキャンバスでサイトを開き、フィルターの動作を Issue と承認済みの計画に照らして確認します。

1. 次のプロンプトを送信し、アプリを起動してブラウザーキャンバスでページを開くよう Copilot に依頼します。

    ```plaintext
    Start the app and open it in the browser canvas.
    ```

2. アプリが起動し、Copilot app 内にブラウザーウィンドウが開いたことを確認します。
3. カテゴリーを選択し、表示結果が一致することを確認します。フィルターをクリアしてからパブリッシャーを選択し、表示結果が一致することを確認します。
4. カテゴリーとパブリッシャーを組み合わせ、結果を Issue と承認済みの計画に照らし合わせます。複数カテゴリーがサポートされる場合は、合意した組み合わせの動作を確認します。
5. ゲームが一致しない組み合わせを試し、空の状態を確認します。フィルターをクリアまたはリセットして、全件が再表示されることを確認します。
6. 確認が終わったら、次のプロンプトを送信し、このセッションで起動した開発サーバーを停止します。

    ```plaintext
    Stop the dev server and close the browser canvas.
    ```

## 次のレッスンに向けてセッションを保持する

フィルター機能の PR はまだ作成またはマージしません。レッスン 4 から 8 まで、同じセッション、worktree、ブランチを使います。次はフィルター機能にカスタム指示を適用し、スキルと QA の改善を追加してから、レッスン 8 で作業をまとめた PR を作成してマージします。開発サーバーを停止した後、セッションはそのままにしておき、次のレッスンで同じセッションに戻ります。

## まとめと次のステップ

異なるエージェントモードを使って機能を構築し、レビューしました。このレッスンでは、次の作業を行いました。

- GitHub Issue から新しいエージェントセッションを開始した。
- **Plan** モードで要件を定義した。
- **Autopilot** モードを使用して新機能を実装した。
- コードをレビューした。
- ブラウザーキャンバスで機能を手動で検証した。
